Les coûts de mint en IPFS sont variables on il une solution pour la mutabilité ?

Coût : Quasi nul (seulement frais de publication IPNS, ~0.0001–0.001 EGLD sur MultiversX si tu utilises un node).

Comment s'assurer que l'on ne détourne pas l'usage du nft sans payer la location ? Le contenu est visible par l'utilisateur ?

Voici une explication claire et réaliste.1. Comment fonctionne le lease sur Itheum (Data NFT-LEASE)Data NFT-LEASE (type spécifique de Data NFT) permet de louer l'accès au contenu pour une durée limitée (ex. 1 semaine, 1 mois, ou custom) sans transfert définitif de propriété.
Le propriétaire (Data Creator) garde le contrôle total : il peut révoquer l'accès à tout moment, limiter la durée, ou ajouter des conditions.
Le locataire (lessee) paie en $ITHEUM (ou autre token) pour obtenir un droit d'accès temporaire.
Techniquement, c'est une "license numérique autonome" : le NFT agit comme une clé d'autorisation (authorization key) qui déverrouille l'accès au contenu (prompts, datasets, etc.) via l'interface Itheum ou SDK.

2. Comment on empêche (ou limite fortement) le détournement sans payerIl n'y a pas de barrière physique absolue (comme dans un DRM centralisé), mais plusieurs couches techniques et économiques rendent le détournement très coûteux ou inutile :Accès gated via smart contract : Le contenu n'est pas "ouvert" dans le NFT lui-même. Le NFT est une clé d'accès qui déclenche l'autorisation via le protocole Itheum. Sans payer le lease (transfert $ITHEUM), le smart contract refuse l'accès. Le locataire doit interagir avec le système Itheum (DataDex, SDK, ou app) pour "unlock" et voir/utiliser les données.
   Contrôle par le propriétaire : Tu (le créateur) peux révoquer le lease à tout moment (freeze ou burn partiel via le control panel Enterprise). Si quelqu'un partage illégalement, tu coupes l'accès.
   Pas de transfert complet : Contrairement à un NFT-FT (full transfer), le lease ne transfère jamais la propriété. Le locataire ne peut pas revendre ou transférer le NFT lui-même sans ton accord (ou via royalties forcées).
   Royalties et traçabilité on-chain : Toute revente ou extension de lease génère des royalties automatiques (ex. 10–25 %). Si quelqu'un essaie de contourner via un marketplace tiers, les royalties peuvent être bypassées (comme sur beaucoup de chaînes), mais Itheum impose des guardrails (limitation trading sur 3rd party marketplaces au début, pour protéger les créateurs).
   Risque économique : Le détournement coûte cher en réputation + frais gas + perte d'accès futur. Si quelqu'un copie le contenu après lease, il perd l'upgrade/mutation (tu peux muter le NFT pour changer le contenu ou ajouter des protections).

Limites réelles : Une fois le contenu unlocké pendant le lease, le locataire peut le copier localement (screenshot, export). C'est le même problème que tout DRM : la copie est possible après accès légitime. Itheum ne peut pas empêcher ça techniquement (aucun système blockchain ne le peut à 100 % pour du contenu numérique). La protection repose sur :Légalité (contrat implicite via Terms of Use + preuve on-chain du lease).
Réputation (si quelqu'un abuse, tu le blackliste ou publies la preuve).
Design incitatif (leasing récurrent est plus rentable que piratage).

Propriétaire vs locataire : Le propriétaire garde le contrôle total (peut muter le contenu, révoquer, voir qui accède via logs). Le locataire a un accès temporaire et révocable.

En résumé pour ton usage (prompts/agents YAAAWP)Prévention détournement : Location = clé temporaire via smart contract + royalties + révocation propriétaire. Pas infaillible contre copie locale, mais très dissuasif (coût + traçabilité on-chain).
Visibilité : Le locataire voit le contenu pendant le lease (c'est le but), mais pas avant paiement, et pas éternellement.
Astuce pratique : Pour plus de protection, rends le contenu "utile mais pas complet" (ex. prompt de base + besoin d'upgrade via mutation payante) ou ajoute watermarking/nonce unique dans les prompts.

You can query as of a specific version: table.to_pandas(version=42) or use version in queries.

Querying "as of" a specific time by finding the version whose timestamp is closest to your target (or the last version before it).
